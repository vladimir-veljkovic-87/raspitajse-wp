## Required dossier

### 1. Census and fingerprints

For every retained vendor root record exact path/name/version, staging active status, deploy treatment, deterministic current tree hash, hashes at `baseline/staging-2026-08` and `baseline/production-2026-08` when present, earliest usable repository import/reference, differences against each local reference, and whether an exact pristine same-version upstream package is locally available and verified.

Use Git tree/blob evidence. Do not hash or inspect production runtime files.

### 2. Provenance status

Assign exactly one:

- `PROVEN_DIRECT_DELTA` — repository evidence proves direct modification;
- `SUSPECTED_PRE_BASELINE_DELTA` — custom behavior exists but no pristine ancestor proves the full delta;
- `NO_REPO_DELTA_PROVEN` — local references match, while upstream cleanliness remains unclaimed;
- `PRISTINE_UPSTREAM_MATCH_PROVEN` — exact-version pristine reference and full-tree match are proven;
- `UPSTREAM_REFERENCE_MISSING` — cleanliness needs an exact pristine package;
- `NOT_RUNTIME_RETAINED` — historical package is not active, deployed or retained.

Never translate `NO_REPO_DELTA_PROVEN` into clean or update-safe. For every proven/suspected delta, group exact paths by purpose and identify affected candidate, employer, job, application, messaging, mail, entitlement/payment, admin, presentation, environment or diagnostics behavior.

### 3. KEEP / CHANGE / DROP map

Map each evidenced delta group:

- `KEEP` only with a current requirement and accepted parity evidence;
- `CHANGE` only with an explicit replacement acceptance criterion;
- `DROP` only when current policy makes it obsolete;
- `UNRESOLVED` when purpose, reference or regression evidence is insufficient.

For every non-`DROP` group record current owner/location, preferred update-safe destination, existing accepted regression evidence, missing proof before restoration/removal, and dependencies on other deltas. Do not classify from filenames alone.

### 4. Undocumented dependency map

Statically identify Raspitajse-owned or child-theme code that calls, includes or overrides a modified vendor symbol/template/behavior. Record dependency direction and whether restoring the vendor delta would break a required flow. Do not execute application flows, fixtures, HTTP, mail, scheduler or payment behavior.

### 5. Ordered follow-ups

Define small follow-up slices, one package or tightly coupled family each. State exact pristine reference needed, delta groups and `KEEP/CHANGE/DROP` actions, owned replacement, focused regression, whether repository-only work or later locks/fixtures are required, rollback boundary and approval blocker. Do not implement them.
