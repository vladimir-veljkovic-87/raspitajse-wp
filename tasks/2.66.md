## Fixed product contract

The candidate-facing vocabulary is:

1. `submitted` — **Prijava poslata**
2. `under_review` — **U razmatranju**
3. `shortlisted` — **U užem izboru**
4. `interview` — **Poziv na razgovor**
5. `hired` — **Primljen/a**
6. `rejected` — **Nije izabran/a**

Rules:

- a new successful application starts as `submitted`;
- candidate can read only own application status;
- employer can act only on applications for jobs owned by its canonical employer identity;
- linked employer employees use the existing canonical parent-employer mapping;
- `hired` and `rejected` are terminal for ordinary employer actions;
- same-status updates are idempotent and create no notification;
- no private CV, application body, email address or internal reason appears in status notifications.

Do not add candidate withdrawal, interview scheduling, offers/contracts, chat redesign or a general ATS in this slice.

## Required implementation

### 1. Canonical application identity and duplicate prevention

- Resolve application, candidate profile/user, job and canonical employer only from saved authoritative relations.
- A candidate/job pair may have at most one non-trashed application.
- Reuse the existing accepted duplicate guard where it is authoritative; close only a proven gap rather than adding a parallel counter.
- Cover frontend, AJAX and ordinary programmatic submission seams used by the current product.
- If concurrency can bypass the existing guard, add one bounded request-scoped advisory lock keyed by blog + canonical candidate + job, recheck while locked, and always release through normal and shutdown paths.
- A duplicate attempt must create zero new application rows, preserve the original application/status and show a localized message equivalent to `Već ste se prijavili na ovaj oglas.`.
- Do not expose another candidate's application existence through forged IDs.

### 2. Canonical status service

- Provide one owned registry mapping canonical status code to escaped localized label, terminal flag and allowed next states.
- Initial state is `submitted`.
- Allowed ordinary employer transitions:
  - `submitted → under_review | shortlisted | interview | hired | rejected`;
  - `under_review → shortlisted | interview | hired | rejected`;
  - `shortlisted → interview | hired | rejected`;
  - `interview → hired | rejected`.
- Terminal states reject further ordinary changes.
- Reject unknown, malformed, stale, disallowed and cross-application transitions before writes.
- Persist only the canonical code and a safe transition timestamp using the existing/owned authoritative field.
- If compatibility mapping from existing vendor states is needed, make reads deterministic and non-mutating; do not bulk rewrite historical applications.

### 3. Employer-isolated status action

- Add/update an employer dashboard action through an existing update-safe hook/AJAX boundary.
- Require logged-in actor, exact nonce, application existence, correct post type, saved job relation and canonical employer ownership.
- A linked employee may act only when the existing parent-employer authorization says it may manage that employer's applications.
- Other employer, candidate, anonymous actor or forged job/application/employer IDs receive a generic denial with zero write.
- Approved administrator bypass, if current product requires it, must be explicit through `manage_options` plus exact application edit capability; never hardcode user IDs.
- Use compare-and-set or equivalent precondition so two stale status requests cannot silently overwrite each other.

### 4. Candidate-visible tracking

- On the existing candidate applications surface, render one status badge/label for each own application.
- Show job title/link, localized current status and safe updated date already allowed by the dashboard.
- Candidate must never see employer-only controls, internal reason codes, other applicants, private notes or raw meta keys.
- Unknown legacy status displays a safe `Status nije dostupan` label and does not mutate data.
- Empty application list and vendor component inactive must render/load safely.

### 5. Owned notification

- Add an explicit application-status channel/integration to Raspitajse Communications.
- Trigger only after a successful real transition commit.
- Resolve recipient from the authoritative application/candidate relation, never request input.
- Send exactly one notification containing safe job title, new localized status and environment-aware candidate-dashboard/application link.
- Never include CV, application message/body, candidate/employer email, private notes or internal failure details.
- Use approved sender policy; user addresses are never `From` or `Reply-To`.
- Duplicate callback, retry or same-status request must not duplicate notification.
- On staging/offline tests, intercept before real transport.

### 6. Compatibility

- Preserve initial application creation, existing employer applicant list, candidate dashboard, role isolation and job ownership.
- Preserve 2.63 private messages, 2.64 desired positions, 2.65 job posting/quota and current job alerts.
- Do not create mail during read/render paths.
- Do not change application status merely by viewing it.
