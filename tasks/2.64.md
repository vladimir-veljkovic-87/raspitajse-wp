## Required implementation

### 1. Canonical term source

- Resolve the existing job-position taxonomy by registered code, never by translated display label.
- Query only active/non-empty-status terms allowed by the current taxonomy contract.
- Offer only terms with a valid parent; root/group terms may be rendered as non-selectable grouping labels when useful.
- Sort deterministically using the existing site order when defined, otherwise by localized name with stable term-ID tie-break.
- Store canonical integer term IDs, not names or slugs.

### 2. Candidate profile UI

- Add the field to the existing frontend candidate profile edit flow.
- Render a multiple select compatible with the current form components and mobile layout.
- Show clear help text: candidate may select at most three positions.
- Existing valid saved selections are preselected.
- Empty selection is allowed and means no position preference yet.
- Do not expose internal meta keys, taxonomy codes or debugging data.
- Client-side maximum-three behavior is helpful UX only; server validation remains authoritative.

### 3. Authoritative save

- Use the existing candidate-profile nonce and ownership/capability boundary, adding a dedicated nonce only if the existing one cannot safely cover the field.
- Only the candidate who owns the profile, or an authorized administrator through the accepted profile flow, may change the selection.
- Normalize to unique positive integer term IDs.
- Reject the entire submitted change atomically when it contains more than three values, a root term, missing term, wrong taxonomy term, malformed value, duplicate/tampered payload after normalization, unauthorized profile or invalid nonce.
- On rejection, preserve the previously stored valid value and return a user-visible validation error through the existing form mechanism.
- On valid empty input, save an empty canonical value without deleting unrelated profile data.
- Never trust hidden labels, slugs, request role or client-side limits.

### 4. Owned read/matching contract

Provide small owned functions/services that:

- return a candidate's validated canonical desired-position term IDs;
- return display-safe term labels for profile presentation;
- determine whether a job's single canonical position overlaps at least one candidate preference;
- treat no preferences as `no preference configured`, not an automatic match;
- ignore stale/deleted/parent/wrong-taxonomy stored IDs without mutating data during reads.

Keep this contract reusable by later job-alert and matching tasks. Do not build a recommendation engine or change current alerts in this slice.

### 5. Compatibility

- Preserve all existing candidate profile fields and saves.
- Preserve registration, login, applications, private messages and job alerts.
- Do not change employer profiles or job forms.
- Existing candidates without the new value continue to load/save normally.
- Code must load safely when the vendor candidate-profile component is inactive.
