- exactly one concrete position;
- a separate required field **“Potreban broj radnika”**;

- Free launch allows a canonical employer, including linked employee accounts, at most three simultaneously active public unexpired jobs.
- Hitting the limit must never lose entered content: saving a draft remains available, while publication is refused with a clear explanation.
- Existing authoritative quota/concurrency code in Raspitajse Commerce remains the only publication authority. Do not create a second counter or parallel quota implementation.

## Required implementation

### 1. Single canonical position

- Use the same registered `job_listing_category` taxonomy and child-term validity contract accepted by 2.64.
- Employer create/edit UI must accept exactly one position term, not an arbitrary multi-select.
- Existing valid selection is preselected during edit.
- A missing, root, nonexistent, wrong-taxonomy, multiple or malformed position selection must prevent publication and return a localized field error.
- Invalid publication attempts preserve title, content and safe submitted metadata in a non-public state wherever the existing flow persists them.
- Editing an existing valid active job without changing its position remains valid.
- Do not change historical jobs during this repository-only task; compatibility reads may classify old multi-position jobs as needing repair without silently rewriting them.

### 2. “Potreban broj radnika”

- Add or normalize one visible field labeled exactly `Potreban broj radnika`.
- Accept a canonical positive integer, defaulting new forms to `1`.
- Enforce a documented sane upper bound in one shared validator; show localized feedback when the value is missing, zero, negative, decimal, malformed or above the bound.
- Store one integer value in the authoritative existing/owned key.
- Display the value safely on employer edit and through a small owned read helper for later public job presentation/application work.
- Do not infer worker count from title, category, vacancies text or duplicate fields.

### 3. Free quota UX

- Reuse the existing canonical-employer resolver and authoritative active-job query from `Raspitajse_Free_Job_Access_Policy`.
- Expose one read-only presentation object: `used`, `limit=3`, `remaining`, and whether the current job already consumes a slot.
- Render a localized summary on create/edit, for example `Aktivni oglasi: 2 od 3`, with a clear explanation at zero remaining.
- UI may discourage/disable publish at the limit but must keep draft save available.
- Server-side authoritative publication continues through the existing quota lock/recount gate across frontend, admin, REST, AJAX and programmatic saves.
- Editing the current active job must not consume a fourth slot.
- Do not use user meta/options/transients as quota authority and do not reintroduce package/order/checkout requirements.

### 4. Unified validation boundary

- Validate position and worker count before a requested public transition.
- Draft saves may preserve incomplete work, but must retain explicit validation state and may never become public until valid.
- Ownership, nonce and capability checks must use current accepted employer flow.
- Employee accounts share the parent employer's quota exactly as in the existing policy.
- Forged employer/profile/job IDs fail closed and cannot view or consume another employer's allowance.
- Reason codes and logs contain no PII.

### 5. Compatibility

- Preserve normal preview, moderation, relist, edit and admin moderation behavior.
- Preserve the existing free package bypass and historical WooCommerce/package data.
- Preserve candidate registration/profile/application, 2.63 private messages, 2.64 desired positions and current job alerts.
- Code loads without fatal error if vendor submit-form symbols are unavailable.
