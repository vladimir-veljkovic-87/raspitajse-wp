## Required integration work

### 1. Boot and namespace compatibility

- Load the complete stacked code in the same deterministic stubbed process.
- Prove no class/function/constant/action/AJAX/asset-handle collision.
- Prove every component boots idempotently and absence of any optional vendor component causes no fatal error.
- Verify shared sender policy channels from messaging and application status coexist.
- Verify owned scripts/styles enqueue only on their intended candidate/employer surfaces and do not leak controls across roles.

### 2. Cross-feature identity consistency

- Candidate profile/user identity used by desired positions, application creation, status display and notification recipient must resolve consistently.
- Canonical employer identity and linked-employee mapping used by job quota, application authorization and messaging must resolve consistently.
- Job position term used by employer posting must be the same canonical `job_listing_category` term consumed by candidate desired-position matching.
- Job and application relationships must be derived from saved state, never request-controlled IDs.
- Any inconsistency must fail closed without partial writes in the integration harness.

### 3. Complete deterministic journey harness

Add one focused cross-feature harness using reserved synthetic IDs/data and WordPress/vendor stubs only. Execute the journey in this order:

1. create/load one candidate and one employer identity;
2. candidate saves three valid desired child positions;
3. employer creates one valid job using one overlapping position and valid workers-needed count;
4. quota presentation changes consistently from `0/3` to `1/3`;
5. matching helper reports overlap;
6. candidate submits one application with initial `submitted` status;
7. duplicate application returns the accepted localized duplicate message and creates nothing;
8. owning employer moves `submitted → under_review → shortlisted → interview`;
9. candidate surface reflects every committed status;
10. each real status change produces one intercepted owned notification and same-status retry produces none;
11. candidate sends one private message to employer and employer replies;
12. each message action produces one owned notification and suppresses only its exact unsafe vendor fallback.

Record assertions only; never print fixture addresses, content, message bodies, CV data or secrets.

### 4. Negative integrated journey

In the same harness prove:

- fourth desired position rejected without changing the first three;
- root position cannot be used by candidate or employer;
- invalid workers-needed value keeps job non-public;
- fourth active job is refused while draft remains possible;
- other candidate cannot read the application;
- other employer cannot change its status;
- terminal application status cannot transition further;
- duplicate/stale callbacks do not duplicate email;
- unrelated mail is not intercepted;
- candidate cannot obtain employer controls and employer cannot obtain candidate profile authority;
- no package/order/cart/checkout/payment/scheduler path is invoked.

### 5. Integration corrections
