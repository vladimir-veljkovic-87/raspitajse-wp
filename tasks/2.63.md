## Product outcome

Develop a real user-facing communication slice: when a candidate or employer sends the first private message or replies, the other participant receives exactly one Raspitajse-owned notification with a safe sender identity and a link back to the conversation.

Required result: `PASS: OWNED_PRIVATE_MESSAGE_NOTIFICATIONS_READY`.

## Current problem

WP Private Message 1.0.7 currently builds the email `From` header from the sender user's private email address in both the initial-message and reply paths. That leaks a user address into transport identity, can fail DMARC/SPF alignment and keeps launch-critical messaging dependent on two direct vendor edits.

Move notification ownership into `raspitajse-communications` without editing `wp-private-message`.

## Required implementation

### 1. Owned sender channel

Add an explicit private-message notification channel to `Raspitajse_Communications_Sender_Policy`.

- Staging must use an existing approved `@stage.raspitajse.com` identity.
- Production resolution must remain configuration-driven and fail closed when a valid approved identity is unavailable.
- Never use the candidate's or employer's email address as `From`, envelope sender or `Reply-To`.
- SMTP credentials remain transport-only.

### 2. Initial-message notification

Subscribe through owned integration code to `wp-private-message-after-add-message`.

- Validate message, sender and recipient IDs and require two distinct real users.
- Require the saved message metadata to match the hook participants.
- Resolve the recipient only from authoritative saved state, never request input.
- Send exactly one owned notification containing safe display context, the message subject, and an environment-aware link to the recipient's message dashboard/conversation.
- Do not include the message body, sender email, recipient email, secrets or private metadata in subject/body/logs.

### 3. Reply notification

Subscribe to `wp-private-message-after-reply-message`.

- Validate reply, parent conversation and current participant against saved parent sender/recipient metadata.
- Notify only the opposite participant.
- A third party, malformed parent, deleted user, self-message or mismatched metadata must fail closed with zero mail.
- Produce one environment-aware conversation link and no message-body disclosure.

### 4. Exact vendor-mail suppression

After an accepted owned notification attempt, suppress only the single legacy vendor mail call that immediately follows that exact initial/reply hook.

- Use bounded in-process state with an exact expected recipient/notification fingerprint and one-call budget.
- Unrelated `wp_mail` calls before or after it must pass unchanged.
- Clear state after the matched call, on mismatch, and at request shutdown.
- If owned delivery fails, suppress the unsafe vendor fallback and record only a sanitized failure signal; never expose a user's email as transport identity.
- Do not globally disable `wp_mail`, the WP Private Message feature or its database message creation.

### 5. Compatibility

- Preserve existing message/reply creation, unread state and AJAX response behavior.
- Preserve the vendor option that enables/disables user notification: disabled means zero owned mail and no suppression state.
- Avoid duplicate delivery when hooks fire twice for the same saved event within one request.
- Load safely when WP Private Message is inactive or its symbols are unavailable.
