## 4. Exact current due/frequency algorithm

WPJBP runs one daily callback, then loops these frequency definitions in this exact order:

| Key | Label meaning | Legacy days |
|---|---|---:|
| daily | daily | 1 |
| weekly | weekly | 7 |
| fortnightly | every two weeks | 15 |
| monthly | monthly | 30 |
| biannually | semiannual | 182 |
| annually | annual | 365 |

For each outer-loop key:

1. Calculate cutoff as raw date format Y-m-d after subtracting the configured number of days from current_time('timestamp').
2. Query all published job_alert IDs whose meta satisfies:
   - _job_alert_send_email_time does not exist; OR
   - _job_alert_send_email_time is less than or equal to that cutoff AND _job_alert_email_frequency equals the current outer-loop key.
3. For each selected alert, query matching published jobs, render, call mail, then delete and re-add _job_alert_send_email_time with today's Y-m-d.
4. Continue to the next frequency key.

Consequences:
- Current comparison is date-only, not an instant/timestamp.
- The value is compared as ISO date-like meta text; no time-of-day is represented.
- Frequency is checked only in the second OR branch.
- An unsent alert enters the first outer iteration, daily, regardless of its stored frequency.
- In a normal single process, a successful metadata rewrite in the first loop prevents that unsent alert from matching later loops on the same day.
- The same alert can nevertheless be selected more than once when the delete/add rewrite fails between operations, when the write is absent, or when parallel workers take their query snapshots before either writes.
- A 15-day value is not a two-week/14-day cadence. Values 30, 182, and 365 are fixed durations, not calendar month, half-year, or year.

## 5. Current send_email_time semantics

The exact honest name for _job_alert_send_email_time is:

last normal-return attempt date written by the legacy callback

It is not:
- last successful delivery;
- SMTP/provider acceptance time;
- inbox delivery time;
- last due evaluation time; or
- a concurrency/idempotency marker.

Write timing and failures:
- It is written after WP_Job_Board_Pro_Email::wp_mail returns.
- The producer discards the wrapper's boolean return.
- If core wp_mail returns false, the date is still written and the failed attempt looks complete until the next frequency period.
- If a WP_Error is introduced by a future owned transport contract but is not explicitly handled, current code has no valid state mapping for it.
- If an exception/fatal/process death occurs before the write, no date is written and the alert remains due.
- If SMTP/provider accepts the message and PHP dies before the write, the next process can send the same alert again.
- The delete followed by add is non-atomic. A failure between them leaves the meta absent, which makes the alert match every subsequent outer-loop NOT EXISTS branch.

## 7. Target due-window contract

Recommendation: calendar cadence in the WordPress site timezone, with all comparison instants stored in UTC.

A regular delivery window is the just-closed site-local calendar period for an alert. Canonical window identity:

alert_id + config_revision + normalized_period_key

Examples:
- daily: D:2026-08-31
- weekly: W:2026-W36, ISO Monday through Sunday
- biweekly: B:2026-W35-36, anchored to a documented even/odd ISO-week epoch
- monthly: M:2026-08
- semiannual: H:2026-H1
- annual: Y:2026

The config revision participates in the window key so an edit cannot collide with an already evaluated window. Job-level history remains keyed independently by alert_id + job_id, so an edit does not automatically resend old jobs.

Regular due rule:
- A window becomes due only after its local end boundary has passed.
- Convert the local start/end boundaries to UTC once with wp_timezone/DateTimeImmutable.
- next_due_at_gmt is the UTC instant of the next local boundary.
- Completing or terminally closing a window advances from the window boundary, never from the actual worker/send time; late cron execution therefore does not drift cadence.
- An active retry keeps the same window key even after a later calendar boundary passes.
- At most one open window per alert is processed. Missed historical windows are coalesced into the oldest current undelivered backlog, not emitted as many emails in one run.

Fixed-duration versus calendar comparison:

| Choice | Predictability | DST/timezone | User expectation | Complexity |
|---|---|---|---|---|
| 1 day | Regular elapsed duration, but wall-clock time shifts over DST | 24 hours is not always one local day | Usually expected as each local day | Low |
| calendar daily | Same local date boundary | Explicit 23/25-hour days handled | Best match | Low |
| 7 days | Anchored to previous attempt and can drift with delayed runs | Wall time can shift | Less clear than a named week | Low |
| calendar weekly | Stable ISO week | Local boundary converted to UTC | Best match for weekly | Low-medium |
| 15 days | Predictable duration but not fortnightly | Drifts through weekdays | Conflicts with two-week expectation | Low |
| calendar biweekly | Stable two-week blocks with documented anchor | DST-safe boundaries | Best match for every two weeks | Medium |
| 30 days | Drifts against month names/lengths | DST plus calendar drift | Poor match for monthly | Low |
| calendar monthly | Natural month boundaries | DST-safe | Best match | Medium |
| 182 days | Drifts against Jan-Jun/Jul-Dec | Leap years and DST distort | Poor match for semiannual | Low |
| calendar semiannual | Jan-Jun and Jul-Dec | Natural local boundaries | Best match | Medium |
| 365 days | Drifts in leap years and against anniversaries/calendar years | Leap-year ambiguity | Poor match for annual | Low |
| calendar annual | One named calendar year | Natural local boundary | Clear if product means annual digest | Medium |

Technical recommendation: calendar cadence. Which frequency choices remain exposed is a business decision in section 25.

Current audit:
- Job publish date is read only for rendering and newest-job extraction, not used as a query eligibility boundary.
- Alert creation time is not used.
- Previous attempt/delivery time is not used in the job query.
- Query requires job post_status=publish and applies the saved WPJBP filters.

- There is no per-alert/per-job marker.
- Featured/urgent changes can alter menu_order and therefore which one result wins, even if the job is old.

Recommended target eligibility for a given alert/window:
- Alert is active, owner exists, account is eligible, canonical candidate profile exists and maps to post_author.
- Job is currently publish/active and not expired at evaluation.
- Job still matches the validated saved WPJBP query.
- job.post_date_gmt is at or after the alert activation cutoff and before the current window's UTC end.
- Job is absent from the durable alert_id + job_id delivered ledger.
- An undelivered job omitted only because of the email cap remains eligible in later windows. Therefore the lower bound is not blindly moved to the previous delivery time; the ledger, not a moving timestamp alone, protects duplicates.
- post_modified_gmt, featured, urgent, and ordinary ordering changes do not make a delivered job eligible again.
- A paid-listing workflow that truly republishes and changes post_date_gmt still does not resend the same job ID under the recommended once-per-alert policy.

This is better than only first-seen/published-within-the-current-window because it prevents capped overflow from being lost. The effective rule is matching + published since activation and before window end + not previously delivered.

## 10. Idempotency-key comparison and canonical choice

| Key | Solves | Does not solve |
|---|---|---|
| alert_id + due_window | Two normal completed sends for one window | Same job across different windows; concurrency before the record exists |
| alert_id + job_id | Same job ever for one alert | Duplicate empty/email evaluation in one window; claim race |
| alert_id + job_id + due_window | Same job twice within one window and permits intentional later resend | Once-ever policy across windows; alert-wide duplicate send |
| Delivery object/ledger ID | Can model attempts, selected jobs, outcomes, and observability | Needs a uniqueness rule underneath; an arbitrary ID alone is not idempotent |

One key cannot represent both business dimensions. Recommended canonical pair:
- window key: alert_id + config_revision + normalized_period_key;
- job key: alert_id + job_id.

The window key prevents a second normal send/evaluation for the same configuration period. The job key enforces the once-per-alert job policy. An atomic per-alert claim prevents two processes from reaching send concurrently. The selected job IDs and stable window key are persisted before mail so retries remain attached to the same logical delivery.

Current save/approval code assigns:

## 15. Minimal target state model and persistence order

No separate persistent due or processing status is needed.

Persistent alert meta, proposed names for 1.88 design review only:
- _raspitajse_cja_next_due_gmt: queryable UTC DATETIME scalar.
- _raspitajse_cja_delivery_state: schema version, config revision/hash, current window key, selected job IDs, attempt count, next_retry_gmt, last evaluated window/time/outcome, and last mail-accepted window/time. It contains IDs/state only, no recipient, body, or saved-query values.
- _raspitajse_cja_delivered_job: repeated job-ID ledger entries, or an equivalently bounded alert-owned collection. The per-alert claim serializes writers; deletion of the alert naturally removes post meta.

Ephemeral processing:
- One non-autoload atomic option claim per alert, described in section 18.

State meanings:
- Due: derived when active alert next_due_gmt is at/before now and no completed record exists for the derived window; it lasts until claimed/completed or rescheduled.
- Processing/claimed: represented only by the atomic option with owner token and TTL; it ends on release or stale recovery.
- Delivered: mail handoff returned true, an accepted marker and selected IDs were persisted, selected IDs entered the ledger, and the window advanced.
- Failed/retryable: same window and selected snapshot remain, attempt count increments, and next_retry_gmt controls retry. No job ledger is written.
- Empty: evaluated outcome, no mail, window advances.
- Terminal failed: the window is closed after the bounded retry count, jobs remain undelivered, and operational state records only code/category and timestamps.

Persistence order:
1. Acquire the per-alert claim.
2. Validate alert/account/profile/config and derive the stable window.
3. Persist current window, exact selected IDs, attempt number, and config revision before mail.
4. If empty, persist evaluated-empty and next due; release.
5. Call owned candidate_alerts transport.
6. On false/WP_Error, persist retry state; never write job ledger.
7. On true, first persist mail-accepted for the exact window/selected IDs. Then reconcile those IDs into the job ledger, persist delivered outcome/next due, and release.
8. Recovery that sees mail-accepted never sends again; it completes ledger/state reconciliation.
9. Unknown schema/state, mismatched config revision, or an impossible transition fails closed and sends nothing.

The irreducible gap remains between provider acceptance and the first accepted-state write; section 17 states the guarantee honestly.

## 16. Mail failure and retry contract

Transport result:
- true means WordPress/PHPMailer accepted the handoff; it does not prove inbox delivery.
- false or WP_Error means failed attempt.
- Exception/Throwable is caught per alert and mapped to a sanitized operational error category; no body, email, query, or PII is logged.

Recommended retry:
- Window remains the same due window.
- Exact selected job snapshot remains attached to that window.
- Maximum three attempts total.
- Backoff from the failed attempt: 1 hour, then 6 hours, then 24 hours.
- Retry uses the same window key and revalidates that selected jobs remain publish/active/matching.
- Active invalid jobs are removed from the snapshot but no new jobs are added mid-retry; replacement waits for the next window.
- After attempt three fails, record terminal-failed for that window, clear retry scheduling, advance to the next regular period, and raise a PII-free operational signal.
- Selected jobs are not marked delivered on failure and may be reconsidered in a later window. Retry is bounded per window; a later normal window is a new product delivery opportunity, not an unbounded tight retry loop.
- Repeated terminal windows should be observable; automatic permanent account/alert disabling is not part of the minimal first slice.

## 17. Crash-after-send and delivery guarantee

Hard case:
1. SMTP/provider accepts.
2. PHP dies.
3. Accepted state is not persisted.
4. Scheduler sees the window as retryable.

Without a provider idempotency API, WordPress plus SMTP cannot know whether the message was accepted and cannot guarantee exactly once.

Trade-off:
- At-most-once: mark complete before sending. Prevents duplicates but loses alerts whenever send fails/crashes after precommit.
- At-least-once: mark only after positive handoff. Preserves eventual delivery but can duplicate in the ambiguous crash interval.
- Effectively-once: claim, stable window/job keys, pre-send snapshot, and accepted-state recovery eliminate normal retries/concurrency duplicates, but the provider-accepted/pre-persist interval still permits a rare duplicate.

Recommendation: at-least-once transport semantics with effectively-once behavior in all observable normal paths. For job-alert UX, a rare duplicate is less harmful than silently losing a delivery. The report and implementation must never claim exactly-once.

Crash recovery:
- Before selection persistence: claim expires; same window is recomputed.
- After snapshot, before mail: claim expires; same snapshot is retried.
- After false, before retry-state persistence: claim expires; same window may retry sooner, but no false success is recorded.
- After true, before accepted-state persistence: ambiguous; duplicate is possible.
- After accepted-state persistence: recovery finalizes ledger/next due without sending.
- After ledger but before window completion: accepted state plus ledger allow idempotent finalization without sending.

## 18. Concurrency claim design

Recommended minimal claim:
- Option key: raspitajse_cja_claim_{alert_id}.
- Value: random ownership token, window key, acquired_at_gmt, expires_at_gmt; no PII.
- Acquire with add_option using autoload=no. wp_options.option_name uniqueness makes one concurrent insert win.
- TTL: 10 minutes. Per-alert execution budget is much shorter.
- Active claim encountered by another worker: skip that alert immediately; do not wait and do not process unrelated state for it.
- Release: delete only when both option name and exact serialized token value match.
- Stale recovery: read the expired value, compare-and-delete that exact value in one SQL predicate, then try add_option once. Never blindly delete a newer owner's claim.
- Owner renews only if its token still matches; unknown ownership fails closed.
- Deleted/missing alert causes exact claim cleanup by the owning/stale-recovery path and no send.

Post-meta add with unique=true is not sufficient as a lock because wp_postmeta has no unique index. A transient is not sufficient because check/set is non-atomic and external object-cache semantics can diverge. The atomic option is the smallest reliable choice at current volume.

## 21. Safe evaluator contract

- Frequency: hourly owned evaluator; first-send latency up to roughly one traffic-triggered run.
- Batch size: 20 alerts maximum.
- Ordering: next_due_gmt ASC, alert ID ASC.
- Pagination: keyset tuple (next_due_gmt, ID), never offset, because processing changes due state.
- Runtime budget: stop starting new alerts at 20 seconds or 50 percent of the available request budget, whichever is lower.
- Per-alert isolation: claim, try/catch/finally, sanitized state result, release. One broken alert cannot stop the rest.
- Maximum one mail attempt per alert per evaluator invocation.
- Continuation: if more exact owned due work remains, schedule one deduplicated single event for the owned evaluator after five minutes. Do not run broad cron or unrelated hooks/actions.
- Retry selection is by exact next_retry_gmt and current window, not by running every pending alert.
- Invalid/unknown state is skipped fail-closed and logged by IDs/state code only.
- No recipient email, body, candidate PII, or plaintext saved-filter values in logs.

## 23. Alert edit/delete/account lifecycle

Delete:
- If the alert is missing/trashed before claim, do nothing.
- If deleted while claimed, re-read before mail; stop, release own claim, and send nothing.
- Alert postmeta/ledger is deleted with the post. Remove only the exact matching claim option; no prefix-wide cleanup.

Frequency change:
- Increment/recompute config revision/hash and next window.
- Do not erase the delivered-job ledger.
- Close any unsent retry snapshot under the old revision; it must not send with stale cadence.
- Apply the approved first-send/reset policy to the new revision. Recommendation: no immediate resend of already delivered jobs.

Filter change:
- Increment config revision/hash.
- Cancel the old unsent snapshot and re-evaluate with new filters.
- Keep alert_id + job_id history so widening/narrowing filters does not resend old jobs.
- Recommendation: allow one initial evaluation for newly matching, never-delivered jobs after the edit; this follows the chosen first-send rule.

Candidate account deactivated:
- Fail closed: no recipient resolution and no send.
- Keep due state without a tight retry; re-evaluate at the next regular operational check after account restoration.

Canonical candidate profile missing or no longer maps to post_author:
- Fail closed with a sanitized lifecycle error.
- Do not fall back to arbitrary candidate_id/user email relationships.

Future edit UI:
- Mutating the existing alert with an explicit config revision is simpler and preserves one sent-job history.
- Creating a new alert version object gives stronger audit history but creates duplicate-history/reset questions and more cleanup.
- Recommendation at current scale: mutate the same alert, increment a config revision/hash, preserve the job ledger. A deliberate delete-and-create is the explicit way to start a wholly new alert/history.

## 24. Legacy lazy migration

Production-safe target for an alert with legacy frequency/query/send_email_time and no owned state:
- Migrate lazily when that exact alert is reached by a bounded migration/evaluator batch; no bulk write.
- Validate post type/status, post_author, candidate profile mapping, allowed frequency, and saved query structure first.
- Legacy JSON saved query may be decoded through the existing compatibility adapter.
- If author is missing but candidate_id maps uniquely to a user, do not silently send; classify for explicit repair/review. Ambiguous ownership fails closed.
- Create config revision/hash from normalized frequency + query, but never log the plaintext query.
- Treat legacy send_email_time only as last normal-return attempt date/cadence evidence. Never backfill a successful delivery or job ledger from it.
- To prevent a migration blast of old jobs, set the migration activation cutoff to the migration instant for previously attempted legacy alerts.
- For never-attempted alerts, use post_date_gmt and the approved first-send policy.
- Derive the next calendar boundary from current site-local time and approved cadence. An already overdue legacy date may cause an immediate empty/new-since-cutoff evaluation, not a replay of historical windows.
- Preserve legacy meta during an observation period but stop writing it after owned cutover. It is a later drop candidate after verified compatibility.
- Invalid frequency/query/owner/profile/state sends nothing and records only alert ID plus sanitized error code.
