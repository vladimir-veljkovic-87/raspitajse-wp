## 3. Job alert lifecycle and specific questions

Storage and owner:

- Stored as published job_alert posts.
- Recipient/owner is post_author and its user_email.
- Creation also writes _job_alert_candidate_id, _job_alert_email_frequency and optionally _job_alert_alert_query.
- Saved query is every submitted POST key beginning filter-. New writes use a serialized PHP array; the sender also accepts legacy JSON.
- The frontend provides add and delete; no dedicated frontend update endpoint was found. Existing objects can be edited through admin/CMB2 and the CPT is exposed to REST.

Due and frequency:

- The sender loops six frequency definitions.
- For an existing send_email_time, due means date-only state less than or equal to site-today minus the configured fixed number of days.
- An alert with no send_email_time is selected by the first outer query regardless of its configured frequency, so its first attempt is immediate.
- send_email_time is the date of the last attempted dispatch, not proof of successful delivery and not a next-run timestamp.

Query and selection:

- WP_Job_Board_Pro_Query::get_posts() maps the saved filter state through WPJBP job query, meta, taxonomy, distance, date and ordering helpers.
- Default ranking is menu_order ascending, then date descending, then ID descending. This prioritizes urgent/featured ordering before pure recency.
- The result query passes post_per_page=1 to the WPJBP helper. The helper intentionally consumes that misspelled internal parameter and maps it to WordPress posts_per_page, so only one matching job is loaded.
- The later array_slice(..., 0, 5), duplicate scan and newest-job scan therefore operate on at most one job.
- The one job becomes newest_job and is removed from job_data; the message is effectively a featured single result, not five results.
- The outer due-alert WP_Query also uses post_per_page instead of posts_per_page directly. There the typo is ignored, so WordPress uses the site default of 10 rather than -1. At most 10 due alert posts are processed by each frequency query.

Templates and recipient:

- Subject/content use WP_Job_Board_Pro_Email::render_email_vars() and current WPJBP DB options, with the vendor default file as fallback.
- job_entry_template is a separate WordPress option used as the repeated partial.
- Headers hardcode a candidate-alert semantic sender and Reply-To on the staging domain.
- Recipient is post_author user_email.
- The mail wrapper result is ignored.

Answers:

1. Can the same alert send the same job more than once? YES. There is no alert-result ledger. A job can be selected in every later due window, on retry after a crash before state update, or by concurrent processes.
2. What is send_email_time? A date-only last-attempt marker written as site-local Y-m-d. It is neither delivery proof nor next due time.
3. When is state written? After the mail wrapper returns, unconditionally.
4. What happens on wp_mail false? The false result is ignored and send_email_time is still advanced, delaying retry until the next frequency window.
5. Does post_per_page change behavior? YES in the outer direct WP_Query: it accidentally caps by the site default 10. In the WPJBP query helper it is the helper's accepted internal key, so value 1 is honored and caps results to one.
6. Do only_one_pass, only_one_ever and duplicate have business effect? only_one_ever is dead. duplicate is ineffective for unique query IDs. only_one_pass is a harmful cross-alert workaround: it is scoped per outer frequency rather than per alert, so only the first selected alert builds content and later alerts can reuse stale content_args.
7. Is the result limited before newest is correctly selected? YES. It is limited to one first, and default ordering is not pure newest because menu_order precedes date.
8. Can the outer frequency loop send multiple frequencies wrongly? Normally an unsent alert is selected in the first iteration, updated, then excluded from later iterations. It does not normally send six times serially. It remains race-prone: concurrent processes or a crash/update failure can duplicate, and the first dispatch ignores the configured frequency.

Empty-result defect:

- There is no found-results guard. With no result, newest_job offsets are read from an empty array and mail composition can continue with incomplete values.

## 8. Idempotency gaps and target contract

Current gaps:

- send_email_time is one date per alert, not a result ledger.
- Expiry notices have no sent marker.
- wp_mail false is treated as attempted/completed.
- Crash after mail but before state update duplicates on retry.
- State before mail would instead lose a message on failure; current code does not solve the atomicity problem.
- Two cron processes can select and send the same work.
- Retry next day either repeats a successful result in a new window or suppresses a failed attempt until the next configured period.

Proposed keys:

| Flow | Deterministic idempotency key |
| --- | --- |
| Admin job expiry | job-expiry-admin + logical admin recipient/channel + job_id + expiry_date/version |
| Employer job expiry | job-expiry-employer + recipient identity + job_id + expiry_date/version |
| Admin candidate expiry | candidate-expiry-admin + logical admin recipient/channel + candidate_id + expiry_date/version |
| Candidate self expiry | candidate-expiry-self + recipient identity + candidate_id + expiry_date/version |
| Candidate to jobs alert | job-alert + alert_id + job_id + due_window_id; message key additionally hashes the ordered selected result IDs |
| Employer to candidates alert | candidate-alert + alert_id + candidate_id + due_window_id; message key additionally hashes the ordered selected result IDs |

Store contract:

- Unique key with states claimed/sending/sent/failed/unknown.
- Atomic insert/claim prevents parallel workers.
- Compose only after claim.
- Definite wp_mail false becomes failed and can retry the same key with a bounded attempt policy.
- Success becomes sent and advances last_success/next_due.
- A crash after transport but before local commit is inherently ambiguous without provider reconciliation. Use a deterministic Message-ID where supported and mark stale sending work unknown; do not blindly resend ambiguous work.
- send_email_time may remain temporarily for compatibility but must not be the source of truth.

## 17. Target architecture

Keep one plugin: raspitajse-communications. Do not create microplugins.

Suggested minimum structure:

- Bootstrap/Transport: retain current gated SMTP behavior and mail-safety compatibility.
- SenderPolicy: semantic channel to validated environment-aware From/Reply-To.
- AlertFrequency: one allowlisted cadence/window contract.
- Scheduler: separate bounded discovery hooks and exact per-object workers.
- JobAlertService: due selection, adapter query, result selection, view model and dispatch.
- CandidateAlertService: same lifecycle, only if business retains the feature.
- ExpiryNoticeService: job/candidate reminder policies selected by business.
- WPJBPAdapter: alert storage/owner, query criteria, domain object snapshots and minimal data access.
- TemplateRenderer: owned subject/body templates and strict allowed view models.
- IdempotencyStore: atomic keys/states/attempts; independent of send_email_time.

Ownership boundary:

WPJBP remains source of:

- Job/candidate domain objects and metadata.
- Alert CPT/meta storage if retained.
- Query/filter helpers.
- Taxonomy/domain lookup.

Raspitajse owns:

- Which flows exist.
- Due/scheduling policy.
- Sender identity.
- Recipient and minimal view model.
- Ranking/selection.
- Templates/content.
- Idempotency/retry/operational logging.

Request path:

Scheduler discovery -> service claim -> WPJBP adapter criteria/query -> deterministic result selection -> minimal view model -> owned renderer -> SenderPolicy -> current Transport -> result/state update.

No service may log or expose the adapter's full candidate object.
