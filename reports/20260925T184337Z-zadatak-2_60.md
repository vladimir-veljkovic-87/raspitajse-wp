## Exact failed LiteSpeed purge path
1. WordPress registers `litespeed_purge_url` to `LiteSpeed\\API::purge_url` in `wp-content/plugins/litespeed-cache/src/api.cls.php`.
2. `LiteSpeed\\API::purge_url` delegates to `LiteSpeed\\Purge::purge_url` in `wp-content/plugins/litespeed-cache/src/purge.cls.php`.
3. `LiteSpeed\\Utility::make_relative` removes the matching site scheme/host, producing `/robots.txt`.
4. `LiteSpeed\\Tag::get_uri_tag` removes any query, applies a trailing slash, and derives `URL.` plus the MD5 of `/robots.txt/`; the observed raw URI tag was `URL.805f5c176b3d416260b25ddef2a538e7`. `/robots.txt` and `/robots.txt/` produced the same tag.
5. `LiteSpeed\\Purge::_add` adds the site/blog and LiteSpeed tag prefixes, builds an `X-LiteSpeed-Purge: public,<tag>` directive, and accumulates it; it does not directly locate or delete a cache file/object.
6. In `LITESPEED_CLI` context the plugin cannot emit the directive to a serving HTTP response. It stores the built directive in the LiteSpeed queue option. `LiteSpeed\\Core::http_header` explicitly returns without sending headers in CLI mode.
7. At CLI shutdown, `LiteSpeed\\Core::send_headers` may initiate a WordPress safe HTTP request to `admin-ajax.php`. A subsequent non-CLI web bootstrap reads the queued directive, emits it as an HTTP response header, and marks the queue drained. LiteSpeed Web Server consumes that response directive in web-request context.
8. Therefore a successful WP-CLI callback observation proves only URL-tag calculation/queueing. It does not prove direct cache deletion or delivery to every upstream cache layer.
