## 4. Canonical employer lookup

Given an explicit positive user ID, the owned module must:

1. fail closed with employer ID `0` if WPJBP is unavailable;
2. call `WP_Job_Board_Pro_User::get_employer_by_user_id( $user_id )`;
3. accept only a positive ID whose post type is `employer`;
4. rely on WPJBP for language-post mapping;
5. not run an independent query or select the “first” reverse-meta match;
6. not mutate user/employer/order state while looking up or reading;
7. not log or expose profile values.

Employee/sub-account checkout behavior is not added by this contract.

## 5. HPOS-safe order writes

| Checkout field | WC order destination | Write method |
| --- | --- | --- |
| `billing_pib` | custom meta `_billing_pib` | `$order->update_meta_data()` |
| `billing_mb` | custom meta `_billing_mb` | `$order->update_meta_data()` |
| `billing_house_number` | custom meta `_billing_house_number` | `$order->update_meta_data()` |
| street + house number | core billing address line 1 | `$order->set_billing_address_1()` |

All writes occur on the `WC_Order` passed to `woocommerce_checkout_create_order`, before Woo's normal save. The callback accepts the hook's `$data` argument and must not use post-meta APIs, direct SQL, or an additional `$order->save()`.

Inputs are scalar-checked and text-sanitized. PIB, MB, postcode and house number must not be integer-cast because leading zeroes, slashes and suffix letters must survive.

The combined address is `trim( sanitized street + one ASCII space + sanitized house number )`. It is derived from submitted street data, never an already merged order value, so repeated execution cannot append the number twice.

Order values are historical snapshots. Later employer-profile changes must not rewrite existing orders. Required-field and business validation semantics stay unchanged; country-specific PIB/MB checksum validation is out of scope.

Every consumer receives or loads a `WC_Order` and uses billing getters plus `$order->get_meta( $key, true )`. Raw order-table queries are allowed only in the test harness as diagnostics.

## 6. Backward compatibility

Compatibility means:

1. retain the same three meta keys;
2. use Woo CRUD for reads and all future writes;
3. do not rename, copy, delete or bulk rewrite historical metadata in 1.66;
4. let orders with missing custom meta render normally;
5. never synthesize current employer data into a historical order.

Application-level raw-`wp_postmeta` fallback is rejected. Under HPOS, an order ID is not a safe general `wp_posts` identity, and fallback could read unrelated/orphan data or mask a failed migration.

Because staging currently reports HPOS authoritative storage with zero CRUD-visible orders, three legacy order posts and twelve orphan target-meta rows:

- 1.66 must not run broad HPOS sync, direct SQL migration, orphan cleanup or compatibility-mode changes;
- aggregate legacy state must fingerprint identically before and after 1.66;
- historical-order recovery requires a separate approval-required task with exact backup, provenance/collision analysis, dry run, idempotency and rollback.
