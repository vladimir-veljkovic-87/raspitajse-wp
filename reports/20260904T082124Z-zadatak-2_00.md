## 10. Current due/time/state semantics

- All four callbacks are registered regardless of configuration; each returns immediately if its flag is false.
- The due helper uses `current_time('timestamp') + DAY_IN_SECONDS * days`, then raw PHP `date('Y-m-d', ...)`, and selects only published objects whose expiry meta equals that one exact date.
- Current site timezone is `+00:00`, offset `0`, so the current computation aligns with UTC and has no DST shift today. The implementation is nevertheless fragile for a future named/non-UTC timezone because it combines a legacy local timestamp, raw `date()` and fixed 86400-second days.
- Exact-date selection has no catch-up range. A missed/delayed daily run loses the notice once the date advances; multiple executions on the same site-local date can resend it.
- There is no sent marker, delivery ledger, claim, batch limit, pagination, maximum runtime, per-record isolation, retry count or backoff.
- `WP_Job_Board_Pro_Email::wp_mail()` returns the `wp_mail()` result, but all four senders ignore it. `false` is indistinguishable from success and there is no retry/state transition.
- Missing/invalid recipients are passed through to `wp_mail`; the employer path can first reference an unset local variable and then falls back to the author email. No canonical-recipient validation exists.

## 13. Bounded target for employer job-expiry notice

- An owned, bounded evaluator operates on the canonical `_job_expiry_date` of published jobs; package entitlement `valid_until` is never used as a notice date.
- Use the configured/product-supported **1 site-calendar day before actual expiry** as the initial deterministic policy. Idempotency key: `job_id + expiry_date + employer_expiry_notice` so an explicit extension creates a new lifecycle window while repeated/delayed runs do not duplicate the same notice.
- Query a small deterministic `expiry_date, ID` batch. Eligible rows must still be `publish`, have a valid future canonical expiry date, and resolve to a canonical active employer/user recipient. Expired, draft, pending, cancelled/deleted or ownerless jobs are skipped fail-closed.
- Use an atomic short claim with ownership token and TTL. A live competing claim skips; stale claims recover. Store successful delivery state only after Transport returns success. Failures retain retryable state with bounded attempts/backoff inside the same notice window; never infinite retry.
- Send through `Raspitajse_Communications_Transport::send(CHANNEL_JOB_EXPIRY, ...)`; do not allow WPJBP to own sender identity.
- Own subject/body in the Raspitajse/configured layer, with only job title, actual listing expiry date and canonical manage/dashboard CTA. Validate all placeholders before send and do not persist or log email/body/PII.
- A delayed evaluator may catch up while the job is still published and before expiry, but the idempotency record prevents a second normal send. No notice is sent after expiry.
- SMTP without provider idempotency cannot guarantee exactly once if the provider accepts and PHP dies before success persistence; the realistic contract is effectively-once with a rare acknowledged duplicate window.
